One job search, three ways to orchestrate it

The same problem (find leads, score fit against the full resume, show the gaps, tailor a resume) solved three ways. What changes between them is who decides the next step. What stays fixed is the data, the scoring rubric, the tracker rules and the evals, which is what lets you compare them fairly.

Measured: scoring one job

A and B scored the same three job descriptions against the same synthetic resume and profile, on the same model (claude-sonnet-5-5), three runs each. Each job has a hand-written gold evidence table, so both are measured against a known right answer as well as against each other. Medians per job:

On these jobs the two approaches judged identically, so the difference is the work around the judgment. A's run loads its skills, reads the profile, tracker and resume through the connectors, writes a fit report and updates the row; B is handed the job description and resume. A run that scores several rows loads the skills once, so A's figure per job falls as the batch grows. The three jobs were written to be unambiguous; borderline jobs, where judgment is more likely to differ, are next. Method, commands and full results: orchestration/job-search/evals/comparison/.

What the comparison shows a reader

  • Choosing who holds control. A puts it in the model, B in code, C splits it: the model decides what to ask, code computes the answer. The ADRs say why each fits its job.
  • Keeping the business rules in one place. The rubric and tracker rules are shared, so a new approach is a new front end, not a rewrite.
  • Measuring instead of asserting. The same synthetic persona and gold scores run against each approach, and the results are in the repo.

What's left is in the roadmap (docs/roadmap.md): borderline cases for the comparison, B to parity with A, and the local MCP server.
